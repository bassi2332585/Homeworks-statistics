Comparative Analysis: Caesar Cipher vs. Toy ECC Scheme

Comparing cryptographic paradigms, mathematical key spaces, and structural security properties

Cryptographic Dimension Caesar Cipher (Symmetric) ECC Scheme (Asymmetric)
Encryption & Decryption Procedure Linear character shift $C_i = (P_i + K) \pmod{26}$. Decryption subtracts $K$. Scalar point multiplication $Q_B = k_B G$, shared secret derivation $S = k_B Q_A$, addition $C = M + S$.
Key Space Size ($\vert{}\mathcal{K}\vert{}$) $|\mathcal{K}| = 26$ (Trivial) Toy: $|\mathcal{K}| = 8$ (Trivial)
Real secp256k1: $|\mathcal{K}| \approx 2^{256}$ (Massive)
Key Distribution Requires a pre-shared secure channel to distribute secret key $K$. Public keys $Q_A, Q_B$ can be transmitted over untrusted, public channels.
Type of Security Lacks statistical security (preserves language letter frequencies). Relies on computational security (hardness of ECDLP), not statistical text masking.

Linear Frequency Retention in Caesar

Because the Caesar cipher maps each character bijectively via a rigid linear shift, the histogram of ciphertext character counts is identical to the plaintext, just shifted. Natural language redundancy (e.g., high frequency of 'E' or 'A') passes directly into the ciphertext.

Computational Hardness in ECC

Unlike classical ciphers, ECC does not aim to "hide letter frequencies" (messages aren't usually mapped to points directly in modern cryptography). Its security comes entirely from the Elliptic Curve Discrete Logarithm Problem (ECDLP): even knowing $G$ and $Q = kG$, finding the scalar $k$ is computationally intractable if the field size is massive (e.g., 256 bits).

Attack Comparison: Caesar vs. Toy ECC vs. Real ECC

Caesar Attack (Statistical): Exploits plaintext language redundancy. Does not require solving a math problem, just measures character distributions.
Toy ECC Attack (Brute-Force ECDLP): Exploits artificially tiny key space ($n=9$). It recovers the exact private key through scalar multiplication without looking at any statistical text feature.
Production secp256k1 Feasibility ($n \approx 2^{256}$): The actual secp256k1 curve operates over a massive 256-bit prime field, giving $n \approx 1.15 \times 10^{77}$. Brute-forcing the scalar would require testing $2^{256}$ combinations. Even optimized algorithms like Pollard's rho ($\mathcal{O}(\sqrt{n}) \approx 2^{128}$ steps) are fundamentally beyond current human computing limits.
